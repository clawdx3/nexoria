# Plan: Fix Pro Agent Memory Integration

## Goal
Make the Pro Agent correctly aware of, access, and persist memories via the Nexoria API — matching the SaaS agent behavior.

---

## 1. Pass `userId` and `sessionId` from the API job to the Pro Agent

### Why
The Pro Agent currently hardcodes `triggeredByUserId: 'pro-agent'` and omits `sessionId`. This means:
- Memories are stored/retrieved under the wrong user.
- Session-tier memories are never loaded.

### Where to change
- `apps/api/src/modules/managed-runtime/managed-runtime.service.ts` — `createJob()` for `native_pro_chat` already includes `chatSessionId` and `userMessageId` in `input`, but NOT `userId`.
- `apps/pro-agent/src/main.ts` — `runJob()` needs to read `userId` from `job.input`.

### Changes
1. In `ManagedRuntimeService.sendChatMessage()`, add `userId` to the job `input` payload when creating a `native_pro_chat` job.
2. In `ProAgent.runJob()`, read `input.userId` and `input.chatSessionId` and pass them into `agent.run()`.
3. In `ProAgentLoop.run()`, use these to construct the `ToolContext` with correct `triggeredByUserId` and `sessionId`.

## 2. Inject a populated `enabledTools` list into the Pro Agent profile

### Why
`AgentToolRegistry.listForContext(ctx)` filters tools by `ctx.agentProfile.enabledTools`. If the array is empty, all tools are exposed. The system prompt generated by `AgentLoopCore.buildSystemPrompt()` also lists tools based on this whitelist. An empty array means the prompt gives the LLM no tool descriptions.

### Where to change
- `apps/pro-agent/src/main.ts` — `runJob()` creates a bare `profile` object with `enabledTools: []`.

### Changes
Set `enabledTools` to the list of all registered tool names from `agent.registry.listAll()`. Or, better: fetch the agent profile from the API (if `NEXORIA_AGENT_PROFILE_ID` is set) so the Pro Agent respects workspace-level tool configuration. Fallback to listing all registered tools.

## 3. Add a real system prompt to the Pro Agent

### Why
The system prompt is empty. The LLM doesn't know its name, role, tools, or memory capabilities.

### Changes
In `runJob()`, set `systemPrompt` to a prompt that:
- Identifies the agent as "Nexoria Pro Agent" with full tool access.
- Mentions memory tools (`search_memory`, `nudge_memory`).
- Describes available tools by iterating `agent.registry.listAll()`.
- Includes a memory fence instruction (optional but consistent with SaaS).

## 4. Deduplicate `NexoriaMemoryProvider` construction

- `ProAgentLoop` constructor creates another one.
- The `SubagentSpawner` is given the manual one, but `ProAgentLoop` never sees it.

### Changes
- Pass the `NexoriaMemoryProvider` created in `main.ts` into `ProAgentLoop`.
- Remove the second construction inside `ProAgentLoop`.
- Also fix the `main.ts` `require` to a regular import.

## 5. Fix `NexoriaMemoryProvider` to pass userId/sessionId correctly

### Current bug
- `store()` passes `ctx.triggeredByUserId` and `ctx.sessionId` correctly.
- `loadTier()` passes `ctx.triggeredByUserId` as `userId` query param — but the API endpoint only filters by `req.user.id` (JWT), not by a `userId` query param.
- Actually looking at `memory.controller.ts`: the `GET` endpoint calls `findByWorkspaceUser(wsId, req.user.id)`. The Pro Agent's `agentToken` might not be tied to a user. We need a way to pass `userId`.

### Option A: Pro Agent uses a service token that scopes to workspace, not user.
In this case, memory reads should be workspace-scoped (all users). The `MemoryService` already supports this if we bypass the `findByWorkspaceUser` filter.

### Option B: Pass `userId` explicitly in query/body.
Add an optional `userId` query param / body field to the memory endpoints, so the Pro Agent can read/write memories scoped to specific users.

**Recommended approach:**
- Add `userId` as an optional query parameter to `GET /workspaces/:workspaceId/memory` (fallback to `req.user.id`).
- Add `userId` to `POST /workspaces/:workspaceId/memory` body.
- This is more flexible and doesn't break the existing SaaS path.

## Risks
- The `agentToken` used by Pro Agent for API calls is `NEXORIA_PRO_AGENT_TOKEN` and may not be in the same scope as a user JWT, so `req.user.id` resolution in the controller may need to be relaxed or we must use workspace-scoped auth.
- Changing the memory controller to accept `userId` from body means any authenticated user could write memories for others in the same workspace. Need validation: only allow if `req.user.id === dto.userId` OR the requester is a service account (Pro Agent token).
