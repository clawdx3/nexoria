# Nexoria Codebase Review — Findings & Recommendations

## 1. CONFIRMED BUGS (by severity)

### Critical

| # | Bug | Location | Fix |
|---|-----|----------|-----|
| 1 | **Ollama default base URL is wrong** — `https://ollama.com/v1` should be `http://localhost:11434/v1`. Every local Ollama deployment fails unless `OLLAMA_BASE_URL` is explicitly set. | `llm-provider.factory.ts:33` | Change default to `http://localhost:11434/v1`. |
| 2 | **Memory semantic search returns random results** — Controller uses `Array(1536).fill(0).map(() => Math.random())` as a mock embedding instead of calling a real embedding model. | `memory.controller.ts:55-56` | Integrate `openai.embeddings.create()` (or similar) before calling `semanticSearch()`. |
| 3 | **`enabledTools: []` grants ALL tools** — Empty array is treated as "no filter" instead of "no tools". Profiles with no tools enabled get full access, a serious privilege escalation path. | `tool-registry.service.ts:29-30` | Return empty array when `enabledTools` is empty. |
| 4 | **Audit log `toDto()` drops the evidence** — Removes `before`, `after`, `reason`, `metadata` fields, making the audit trail useless for investigation. | `audit.service.ts` | Include all fields in the DTO (or create separate summary/detail DTOs). |
| 5 | **No `data-source.ts` exists** — `AGENTS.md` documents `typeorm migration:generate -d src/data-source.ts` but the file does not exist, so migration generation cannot work. | Missing file | Create `apps/api/src/data-source.ts` with the same TypeORM config as `app.module.ts`. |

### High

| # | Bug | Location | Fix |
|---|-----|----------|-----|
| 6 | **Playbooks `toDto()` drops `triggers` and `variables`** — These are the core automation logic fields and are silently omitted from API responses. | `playbooks.service.ts` | Include `triggers` and `variables` in `toDto()`. |
| 7 | **Missions `toDto()` drops `description`, `parentTaskId`, `context`** — Critical fields lost in API responses. | `missions.service.ts` | Include all fields in `toDto()`. |
| 8 | **`tokensUsed: 0` on failure/max-steps paths** — Token counts from intermediate `generate()` calls are discarded. Failed runs always report 0 tokens even if they burned hundreds. | `agent-executor.service.ts:89,100` | Accumulate tokens across all steps and report the total. |
| 9 | **`roles.guard.ts` is completely non-functional** — After checking user exists, it unconditionally returns `true`. The `@Roles()` decorator sets metadata but the guard never enforces it. | `roles.guard.ts:18` | Implement workspace role check using `WorkspaceMembersService`. |
| 10 | **`session` tier loads ALL session entries without sessionId filter** — Acts as user-level memory instead of session-scoped. | `memory-context.builder.ts` | Add `sessionId` filter to session-tier queries. |
| 11 | **No API key validation for `openai`/`openrouter` providers** — Missing keys cause runtime crashes without informative errors. Only `ollama` validates. | `llm-provider.factory.ts` | Add `if (!apiKey) throw Error(...)` checks for all providers. |

### Medium

| # | Bug | Location | Fix |
|---|-----|----------|-----|
| 12 | **Broken test in `tool-registry.service.spec.ts:17-19`** — Asserts `search_products` tool exists but it was never registered. Test will fail. | `tool-registry.service.spec.ts` | Remove `search_products` from expected list or register it. |
| 13 | **Cross-workspace updates possible in `missions` and `playbooks`** — `update()` uses `repo.update(id, dto)` without checking `workspaceId`, allowing cross-workspace data modification. | `missions.service.ts`, `playbooks.service.ts` | Add `workspaceId` to the update WHERE clause. |
| 14 | **Semantic search with pgvector NOT IMPLEMENTED in agent-runtime** — `MemoryContextBuilder.loadTier()` uses simple `find()` ordering. The `embedding` column and `<=>` operator are never used, despite AGENTS.md documenting it. | `memory-context.builder.ts` | Implement embedding-based similarity search for `long_term` tier. |
| 15 | **Three redundant task-creator tools** — `delegate_task`, `create_internal_task`, `create_task` overlap heavily (same underlying operation with slightly different parameters). Wastes prompt tokens and confuses the LLM. | `tool-registry.service.ts` | Merge into one `create_task` tool with all parameters. |
| 16 | **`autonomyLevel` is dead metadata** — Set on `AgentContext` but never read by any subsystem (executor, registry, LLM, memory, reflection). | `agent-runtime.controller.ts:68` | Use it for tool risk gating (e.g., low autonomy = block risk-3 tools) or remove it. |
| 17 | **No context window management** — Messages array grows unbounded across 10 steps. After detailed tool outputs, context may exceed model limits (especially 8K-16K window models). | `agent-executor.service.ts` | Add sliding window with summarization for long conversations. |

## 2. ARCHITECTURE & CODE QUALITY IMPROVEMENTS

### Services to refactor

| Module | Issue | Recommendation |
|--------|-------|----------------|
| `managed-runtime.service.ts` (841 lines) | Largest god file, violates AGENTS.md guidance. Handles instances, jobs, chat sessions, commands, events, bootstrap, context assembly, policy enforcement. | Split into `RuntimeInstanceService`, `RuntimeJobService`, `RuntimeChatService`, `RuntimeBootstrapService`, `RuntimeContextBuilder`. |
| `managed-runtime.controller.ts` (181 lines) | Defines 3 controllers in one file. | Split into `managed-runtime.controller.ts`, `runner.controller.ts`, `artifacts.controller.ts`. |
| `mcp.service.ts` (561 lines) | Tool logic mixed with transport handling. | Extract tool registration into `McpToolRegistry`, keep transport in `McpService`. |
| `social-post-drafts.service.ts` | `create()` has dual return paths (with/without review task), producing inconsistent response shapes. | Always return the same DTO shape; run review-task creation asynchronously. |

### Cross-cutting concerns

| # | Issue | Recommendation |
|---|-------|----------------|
| 21 | **No global JWT guard** — Each controller manually adds `@UseGuards(JwtAuthGuard)`. Endpoints without it are publicly accessible. | Register `JwtAuthGuard` as `APP_GUARD` globally, use a `@Public()` decorator for opt-out routes (login, register). |
| 22 | **`toDto()` inconsistency** — Some modules drop critical fields (missions, playbooks, audit), others include everything. Appears to be copy-paste drift. | Standardize: create a `toResponseDto()` convention that includes all non-sensitive fields. Use `class-transformer` `@Expose()` / `@Exclude()` for declarative control. |
| 23 | **No pagination on list endpoints** — Tasks, missions, playbooks, memory, audit, agent-profiles all lack pagination. Only `attachments.list()` has a `limit` parameter. | Add `skip`/`take` query params to all list endpoints. Use a shared `PaginationDto`. |
| 24 | **No soft-delete pattern on workspace-scoped entities** — Only `attachments` and `users` use soft-delete. Deleting a workspace leaves orphaned child rows with no cascade. | Implement soft-delete + cascade soft-delete for workspace removal. |
| 25 | **Workspace scoping is inconsistent** — Tasks/memory always enforce `workspaceId`; missions/playbooks/social-post-drafts skip it in find/update operations. | Always include `workspaceId` in all queries for workspace-scoped entities. |
| 26 | **Inline DTOs in controllers** — `integrations.controller.ts`, `agent-runtime.controller.ts` define DTO classes inline rather than in `dto/` directories. | Move all DTOs to dedicated `dto/` directories. |
| 27 | **`managed-runtime` context assembly has 41-line instruction array** with some contradictory/social-media-specific instructions. | Move instructions to per-agent-profile config; let them be workspace-customizable. |
| 28 | **`delegate_runtime_job` MCP tool has hardcoded "content creator → social media agent" routing** inline. | Make agent routing rules configurable per workspace. |
| 29 | **`open-webpage.tool.ts` uses dynamic `import('playwright')` via `new Function()`** — Bypasses module resolution, fragile in containers where Playwright may not be installed. | Move to proper DI-injected service with graceful fallback. |
| 30 | **`ToolContext = {...ctx}` is a shallow copy** — Nested objects (`agentProfile`, `modelConfig`) share references. If a tool mutates `modelConfig`, subsequent LLM calls are affected. | Deep-clone or use immutable patterns. |

## 3. SECURITY IMPROVEMENTS

| # | Issue | Recommendation |
|---|-------|----------------|
| 31 | **No rate limiting** on any endpoint. `/auth/login` is wide open for brute-force attacks. | Add `@nestjs/throttler` with tiered limits: strict for auth (5 req/min), moderate for API (100 req/min). |
| 32 | **CORS enabled for all origins** — `app.enableCors()` with no options. | Restrict to the frontend origin via `CORS_ORIGIN` env var. |
| 33 | **No token revocation mechanism** — JWTs live for 7 days with no way to invalidate. No logout endpoint. | Add a token blacklist in Redis (checked on each request via guard), or switch to short-lived access tokens + refresh tokens. |
| 34 | **OAuth tokens stored as plain JSONB** in `integrations.credentials` — no encryption at rest. | Encrypt credentials column using a symmetric key from env vars (e.g., `@nestjs/config` with a custom transformer). |
| 35 | **Hardcoded fallback secrets** in source code: JWT `'change-me'`, runner token `'dev-runner-token-change-me'`, DB password `'nexoria'`. | Remove fallbacks; throw on missing required env vars in production. |
| 36 | **No input sanitization** beyond `class-validator`. String content is stored/returned as-is. | Sanitize user-generated text fields (content, descriptions, comments) for XSS before storage or response. |
| 37 | **No Helmet** — Missing security headers (CSP, HSTS, X-Content-Type-Options, etc.). | Add `helmet` middleware globally. |
| 38 | **No CSRF protection** (relevant if switching to cookie-based auth). | If token-based auth stays, this is lower priority. |
| 39 | **No global exception filter** — Error responses may leak stack traces in non-production modes. | Add `AllExceptionsFilter` that strips stack traces in production. |
| 40 | **`bcrypt` cost factor 10** — Industry recommendation is 12+ for production. | Bump to 12 (or make it configurable via env var). |
| 41 | **`audit.controller.ts` exposes a public `POST` endpoint** for writing audit logs — anyone can inject fake entries. | Make the `POST` endpoint internal-only (runner guard or removed entirely; audit entries should only be written by backend services). |
| 42 | **No workspace role enforcement on mutations** — Any member of any role can modify/delete workspaces, profiles, missions, playbooks, drafts. | Enforce `owner`/`admin` checks in mutations. Use `RolesGuard` (fix it first) with per-endpoint role requirements. |
| 43 | **`@nestjs/throttler` not installed** — Missing dependency for rate limiting. | Install and configure. |

## 5. FEATURE IDEAS / ADDITIONAL FUNCTIONALITIES

### High-impact features

1. **Multi-model A/B testing dashboard** — Compare agent runs with different models/providers side-by-side. Store `modelProvider` + `modelName` on `RuntimeJob` results, show cost/latency/quality metrics per model.

2. **Agent skill marketplace** — Let workspaces share agent profiles and playbooks as templates. Add a `published` flag and a discovery endpoint. Like a plugin store but for agent configurations.

3. **Conversation transcript export & analytics** — Export chat sessions as PDF/Markdown. Analytics: message count, tool call frequency, token spend per session/workspace/agent, success rate.

4. **Scheduled/recurring agent runs** — Cron-based trigger for playbooks. A playbook with `triggers: [{ type: 'cron', value: '0 9 * * 1' }]` auto-runs an agent on Monday mornings. Requires a scheduler service (BullMQ repeatable jobs).

5. **Human-in-the-loop (HITL) approval with Slack/Email integration** — When an agent needs approval, send a Slack message or email with approve/reject buttons. Decouple approvals from the web UI only. The `Integration` providers (Gmail, Meta) already exist — extend to Slack/Teams.

6. **Cost tracking & budget alerts** — Track token spend per workspace/agent. Set monthly budgets, alert when approaching limits. Store cost in `runtime_jobs.metadata.cost` or a dedicated `usage` table.

7. **Agent memory dashboard (admin UX)** — Visualize what an agent "knows": list memory entries by tier, show confidence distribution, let admins prune/curate entries. The data model exists (`MemoryEntry` with `positiveUses`, `negativeUses`, `expiresAt`) but there's no UI to manage it.

8. **Multi-agent collaboration (swarm/orchestration)** — The orchestrator already exists. Extend it so an orchestrator agent can spawn multiple specialist agents in parallel (e.g., research agent + social agent + email agent working on the same mission), then aggregate results.

### Medium-impact features

9. **Webhook triggers for playbooks** — In addition to cron, allow webhook triggers: `POST /workspaces/:wsId/playbooks/:id/trigger` with a signed payload. Useful for CI/CD integrations, form submissions, etc.

10. **Agent version history & rollback** — Keep a changelog of agent profile updates. Allow reverting to a previous version. Store history in a `agent_profile_versions` table or use the audit log (once fixed).

11. **Built-in embedding model for memory** — The `MemoryService.semanticSearch()` already has the pgvector infrastructure. Add auto-embedding on `MemoryEntry` creation using OpenAI `text-embedding-3-small` or a local model (Ollama). This makes the 4-tier memory actually semantic.

12. **Task dependency graph** — Tasks already exist. Add `parentTaskId` / `blockedByTaskIds` to create dependency chains. The agent can then reason about task ordering. Visualize in the frontend as a DAG.

13. **Custom tool builder (low-code)** — Let workspaces define custom tools via a form: name, description, JSON schema for args, and a webhook URL. When the agent calls the tool, Nexoria POSTs to the webhook and returns the result. Complements the existing MCP tool pattern.

14. **Agent persona library** — Pre-built system prompts, tool configurations, and model settings for common use cases: "Customer Support Agent", "Code Review Agent", "Content Writer", "Data Analyst". The built-in profiles already seed 4; expand to 15-20.

### Lower-priority but interesting

15. **Voice/audio input for chat** — Integrate a speech-to-text service (Whisper via OpenAI or local) so users can speak to agents instead of typing.

16. **Agent playground/sandbox** — A testing page where you configure an agent profile, type a test message, and see the full agent loop trace (each step, tool calls, memory loaded, tokens used) before deploying to production.

17. **Integration health dashboard** — Show which OAuth tokens are expiring soon, last sync time, error rates per integration type. The `Integration` entity has `lastSyncedAt` and `expiresAt` but they're never displayed.

18. **Document ingestion pipeline** — Upload PDFs, web pages, or documents; chunk them; generate embeddings; store as long-term memory entries. The agent can then reason over uploaded knowledge bases.

19. **Agent performance leaderboard** — Across a workspace, rank agents by: tasks completed, approval acceptance rate, user rating (thumbs up/down on responses), average response time.

20. **Dark launch / shadow mode for agents** — Run a new agent profile in "shadow mode" alongside the production one. Compare outputs without affecting users. Useful for testing prompt changes safely.
