# Plan: WebSocket-based Agent Chat + Secure Pro Agent

## Goal
Replace the current HTTP polling model with real-time WebSocket communication for all chat (both `native_saas` and `native_pro`). The Pro Agent connects to the API over a secure WebSocket with Ed25519 authentication (no polling, no shared secret tokens). Non-chat tasks continue to use the `RuntimeJob` DB queue but are delivered to the Pro Agent via WebSocket when connected.

## Architecture

### 1. API — NestJS Socket.IO Gateway (`AgentRuntimeGateway`)
- **Namespace**: `/agent-runtime` (Socket.IO namespace)
- **Auth**:
  - **FE clients**: `connect` query param `token=<JWT>` → validated by existing `JwtAuthGuard` logic (extracted into a reusable `JwtSocketGuard`). Rejects unauthorized.
  - **Pro Agent**: `connect` query param `challenge=<signed_nonce>` → validated by `ProAgentSocketGuard`. Handshake:
    1. API generates a random nonce on each `connection` event, sends `auth_challenge` event to the socket.
    2. Pro Agent signs the nonce with its Ed25519 private key and sends back `auth_response` event with the signature and its `instanceKey`.
    3. API verifies the signature against the public key registered in `RuntimeInstance.metadata.ed25519PublicKey`. If valid, the socket is associated with that instance and joins a room `workspace:<workspaceId>` and `instance:<instanceKey>`.
- **Rooms**:
  - `workspace:<workspaceId>` → FE clients + Pro Agent (for chat events)
  - `instance:<instanceKey>` → targeted job delivery to a specific Pro Agent
- **Events emitted** (to FE):
  - `chat.user_message` — user message persisted
  - `chat.assistant_delta` — streaming token (native_saas + native_pro)
  - `chat.assistant_final` — final message with full payload
  - `chat.status` — tool call status
  - `chat.error` — error message
  - `chat.typing` — Pro Agent only, when it starts running a job
- **Events listened** (from FE):
  - `chat.send` — payload `{ sessionId, content, attachmentIds? }`
- **Events listened** (from Pro Agent):
  - `job.claim` — empty payload; API atomically pops the next queued `native_pro_chat`/`native_pro_task` for this instance (same `claimNextJob` logic, but returns directly over WS instead of HTTP)
  - `job.complete` — payload `{ jobId, status, result?, error? }`
  - `job.event` — payload `{ jobId, type, level, message, metadata }`
  - `chat.chunk` — payload `{ sessionId, jobId, content }` → API fans out as `chat.assistant_delta` to `workspace:<wsId>`
  - `chat.final` — payload `{ sessionId, jobId, content }` → API saves to DB as `assistant` message with `[Pro Agent]\n` prefix, emits `chat.assistant_final`, schedules reflection

### 2. `ManagedRuntimeService` — `sendChatMessage` refactoring
- **All agents** emit events through `AgentRuntimeGateway.emitToWorkspace(workspaceId, event)` instead of the in-memory `Subject`.
- **Path A (`native_saas`)**: `AgentLoopService.run()` callback stays the same but the `emitChat` call now goes through the Gateway. FE gets real-time streaming.
- **Path B (`native_pro`)**:
  1. Find `ready` Pro Agent instance for workspace.
  2. If **connected via WebSocket**: emit `chat.typing` + `job.pushed` directly to the `instance:<instanceKey>` room. The job is still persisted as a `RuntimeJob` row for traceability but its status is set to `running` immediately (no `queued` state). Return `{ message, session, jobId }`.
  3. If **offline**: persist job as `queued`, emit a `chat.status` to FE saying "Pro Agent offline, queued", return `{ message, session, jobId }`. When the Pro Agent reconnects, it calls `job.claim` and gets the queued job(s).
- **Remove** in-memory `chatStreams` Subject and `streamChatEvents` SSE endpoint. Replace with Gateway.

### 3. Frontend (`chat.store.ts`)
- On workspace mount / chat page open, open Socket.IO connection to `/agent-runtime?token=<JWT>`.
- `sendMessage` emits `chat.send` event instead of `POST .../run/...`.
- Listen to `chat.*` events, append `assistant_delta` tokens into a buffer, commit on `assistant_final`.
- On disconnect, show reconnecting indicator; on reconnect, re-emit `chat.send` if there is an unsent pending message.
- Remove `runNexoriaChat`, `actionCardPolling`, and `appendWorkspaceActionCards` from the chat flow. Action cards will be pushed from the API via `chat.action_card` event when tasks/approvals are created (reuse existing `TasksService` streamWorkspaceEvents + pipe through Gateway).

### 4. Pro Agent Container (`apps/pro-agent/`)
- **Remove HTTP polling entirely** (`api-client.ts` → `WsProAgentApiClient`).
- **Key generation**: On first startup, if no `ed25519_private_key.pem` exists in `./data`, generate an Ed25519 key pair (using `tweetnacl` or `node:crypto`), store private key, and send the public key during `registerInstance` (stored in `RuntimeInstance.metadata.ed25519PublicKey`).
- **Connection**:
  - Connects to `ws://api:3000/api/agent-runtime`.
  - On `auth_challenge`, signs nonce and sends `auth_response`.
- **Message loop**:
  - On `job.pushed` or after `job.claim` response, run the job via `ProAgentLoop`.
  - While running, emit `chat.chunk` / `chat.final` for chat jobs; `job.event` for task jobs.
  - On finish, emit `job.complete`.
- **Heartbeat**: Still sends HTTP `POST /heartbeat` every 15s (or switch to Socket.IO `ping` built-in). Keep HTTP heartbeat for simplicity — it's lightweight and keeps the DB row alive.
- **Registration**: Keep `POST /runner/runtime/instances` (restore only this endpoint; the rest will go away). Guard it with a new `ProAgentHttpGuard` that verifies a **signed** registration payload instead of `X-Pro-Agent-Token`.

### 5. Security — Ed25519 Auth Flow
- **Key generation** (Pro Agent side):
  - Ed25519 key pair generated once on first boot.
  - Private key never leaves the container (stored in volume `pro_agent_data`).
- **Registration**:
  - Pro Agent sends `POST /runner/runtime/instances` with body `{ instanceKey, workspaceId, mode, version, metadata: { ed25519PublicKey } }` signed with its private key in a `X-Pro-Agent-Signature` header (sign the JSON body).
- **WebSocket handshake**:
  - API sends `{ nonce }` on `auth_challenge`.
  - Pro Agent signs `nonce` and sends `{ signature, instanceKey }` on `auth_response`.
  - API looks up `instanceKey`, gets `ed25519PublicKey`, verifies `signature === sign(nonce, privateKey)`. If ok, mark socket as authenticated and associate with `RuntimeInstance`.
- **Future hardening**: mTLS can be layered on top later (Caddy/Traefik terminates client cert, passes `X-Client-Cert-Hash` to API). Ed25519 stays as a fallback/authz layer.

### 6. Non-Chat Tasks (RuntimeJob, non-chat types)
- `createJob` still persists to DB as `queued`.
- When Pro Agent calls `job.claim`, the API runs the same atomic `UPDATE ... SET status = 'running'` query as today.
- If Pro Agent is **connected via WebSocket** and a new non-chat job is created, optionally emit a `job.available` event to `instance:<instanceKey>` so the Pro Agent can claim immediately instead of waiting for its claim loop.
- Pro Agent still calls `job.event` and `job.complete` over WS.

### 7. DB / Entity Changes
- `RuntimeInstance`:
  - Add column `ed25519PublicKey`? No — keep it in `metadata` as today to avoid a migration for this plan.
  - Add column `wsSocketId`? No — in-memory map `instanceSockets: Map<instanceKey, Socket>` in the Gateway is sufficient.
- No other entity changes needed (chat messages, jobs, sessions remain the same).

### 8. Fallback / Resilience
- If FE socket disconnects mid-stream, messages are still persisted in DB. On reconnect, FE fetches `GET /chat/sessions/:id/messages` to backfill.
- If Pro Agent disconnects mid-job, the `RuntimeJob` row stays `running`. On reconnect, the Pro Agent can call `job.claim` again; if the job is still `running` and assigned to this instance, API returns it (so the Pro Agent can resume or re-run). We add `job.claim` to also return `running` jobs assigned to this instance that have not been completed yet, within a timeout window (e.g. 5 minutes since `startedAt`).

## Open Questions
1. Should we keep the existing SSE `/chat/sessions/:id/events` endpoint as a fallback for non-WebSocket clients, or drop it entirely?
2. Should the Pro Agent's internal `AgentLoopCore` stream chunks over WS as raw text, or should we add a binary framing protocol (e.g. MessagePack) for lower overhead?
3. Do we want to allow multiple Pro Agent instances per workspace (load balancing), or enforce one `ready` instance per workspace? (Current code already returns first `ready` instance.)

## Appendix: Nanobot-Inspired Features to Adopt

After reviewing [HKUDS/nanobot](https://github.com/HKUDS/nanobot), the following features are highly relevant to Nexoria (excluding chat channels and local file-based memory, which we deliberately avoid).

### A. `ask_user` Tool (Blocking Approval / Choices)
**Priority: HIGH**
- Nanobot raises an `AskUserInterrupt` that pauses the agent loop mid-turn.
- Supports structured `options` (e.g., "Approve", "Reject", "Edit").
- Maps cleanly to Nexoria's existing `ApprovalsModule`.
- **Implementation**: Add `ask_user` to `ToolRegistryService`. When called, create an `Approval` row with `status='pending'`, emit a `chat.status` event to FE, and pause the agent loop. Resume when the user submits a decision via the approval endpoint or WS event.

### B. Concurrent Tool Execution
**Priority: HIGH**
- Nanobot partitions tool calls into batches: `concurrency_safe` tools run in parallel; `exclusive` tools (like `ask_user`) run alone.
- **Implementation**: In `AgentExecutorService`, after parsing tool calls from LLM output, group independent calls and `Promise.all()` them. Maintain role alternation by ordering results correctly.

### C. Context Compaction (Microcompact + Snip)
**Priority: HIGH**
- **Microcompact**: Replace old tool result messages with placeholders (`[tool_name result omitted]`) after N steps to save tokens.
- **Snip**: Before each LLM call, estimate token count. If over budget, hard-truncate history while preserving `user→assistant→tool` role alternation.
- **Implementation**: Add a `_microcompact()` step in `AgentExecutorService` before building the prompt. Use tiktoken or a lightweight estimator for token counting.

### D. Self / Introspection Tool (`my_config`)
**Priority: HIGH**
- Nanobot's `MyTool` lets the agent read and modify its own runtime config (e.g., `check max_iterations`, `set model=gpt-4o`).
- Has a scratchpad for session-persistent notes.
- Blocks sensitive fields (`api_key`, `jwtSecret`, etc.) from modification.
- **Implementation**: Add `my_config` to `ToolRegistryService`. Expose read access to `AgentProfile` fields and a `scratchpad` JSONB on `RuntimeChatSession.metadata`. Block writes to sensitive keys.

### E. Cron / Scheduled Task Tool
**Priority: MEDIUM**
- Nanobot has a `CronSchedule` dataclass supporting `every`, `cron`, and `at` schedules.
- Natural language parsing: "remind me tomorrow at 9am".
- **Implementation**: Extend `TasksModule` with a `TaskSchedulerService` using `node-cron` or `bullmq` for recurring jobs. Add a `schedule_task` tool that accepts natural language or cron expressions and stores the schedule in a new `scheduled_tasks` table.

### F. Office Document Reading
**Priority: MEDIUM**
- Nanobot reads `.docx`, `.xlsx`, `.pptx`, and `.pdf` using `pymupdf` and custom extractors.
- **Implementation**: Add `analyze_document` capability to SaaS `ToolRegistryService` (or as a preprocessing step in `AttachmentsService`). Use `mammoth`/`xlsx`/`pdf-parse` npm packages. Reuse the Pro Agent's existing `analyze_document` tool logic.

### G. Notebook Editing (`notebook_edit`)
**Priority: LOW**
- Cell-level `.ipynb` manipulation: `replace`, `insert`, `delete`.
- **Implementation**: Add to Pro Agent tool registry only (too niche for SaaS). Useful for data-science-heavy workspaces.

### H. Crash Recovery Checkpoints
**Priority: MEDIUM**
- Nanobot persists turn state after each phase (`awaiting_tools`, `tools_completed`, `final_response`).
- **Implementation**: After each step in `AgentExecutorService`, write a checkpoint to `RuntimeChatSession.metadata.checkpoint`. On restart/resume, read it back to restore the loop state instead of starting from step 1.

### I. File Read Deduplication (`FileStateStore`)
**Priority: MEDIUM**
- Per-session tracking of file reads with mtime + content hash.
- Prevents infinite loops where an agent re-reads the same file.
- **Implementation**: Add a lightweight in-memory `FileStateStore` scoped to the `RuntimeChatSession` or `RuntimeJob`. Key: `path+offset+limit`, value: `{mtime, hash}`.

### J. Response Templating (Jinja2)
**Priority: LOW**
- Nanobot uses Jinja2 markdown templates for system prompts, identity, skills, etc.
- **Implementation**: Refactor `MemoryContextBuilder` to render `.md` templates from `templates/agent/` instead of inline string concatenation. Makes prompt engineering easier and version-controlled.

### K. Dream — Scheduled Heavyweight Memory Consolidation
**Priority: LOW**
- Cron-scheduled two-phase process: Phase 1 analyzes history + memory; Phase 2 delegates to an agent with `read_file`/`edit_file` tools to make targeted incremental edits.
- **Implementation**: Extend `ReflectionService` with a scheduled "Dream" pass. Instead of just extracting memories, let the agent use tools to update `AgentProfile.systemPrompt`, create `Playbook` entries, or prune stale `MemoryEntry` rows.
