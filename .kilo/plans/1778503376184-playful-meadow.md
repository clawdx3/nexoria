# Plan: Nexoria Two-Tier Agent Platform

## Vision

Nexoria is a platform for non-technical users to run AI agents. Two tiers:

| Tier | Runtime | Location | Tools | Models (v1) |
|------|---------|----------|-------|-------------|
| **Lite** | `native_saas` | In-process (API container) | Safe tools only (riskLevel <= 2): tasks, memory, search, integrations | Default (gpt-4o-mini or similar) |
| **Pro** | `native_pro` | Nexoria-managed VPS | Full tools: shell, fs, code execution, browser | Default (gpt-4o or similar) |

Future: model selection per agent, BYOA (bring your own API key).

- `native_pro` push: when Pro Agent connected via WS, job status set to `running` immediately and pushed via `job.pushed` to instance room

### 1.3 Frontend WebSocket client [DONE]

### 1.4 Pro Agent WebSocket client [DONE]

- `registerInstance()` via signed HTTP POST (Ed25519 signature in `X-Pro-Agent-Signature` header)
- `heartbeat()` via HTTP every 15s
- `claimNextJob()` via WS `job.claim` with 5s timeout fallback
- `emitChatChunk()` / `emitChatFinal()` / `emitJobComplete()` / `emitJobEvent()` over WS
- `onJobPushed()` callback for instant job delivery
- Fallback claim loop still runs alongside WS push

### 1.5 ProAgentRunnerController [DONE]

### 1.6 ProAgentHttpGuard [DONE but not wired]

## Phase 2: Nexoria-Managed VPS Provisioning [TODO]

### 2.1 VPS Provider Abstraction
Create `apps/api/src/modules/vps-provisioning/`:

**Entities:**
- `VpsProvider` — cloud provider config (Hetzner, DigitalOcean, etc.) with API key (encrypted)
- `VpsInstance` — a provisioned VPS (provider, region, size, IP, status, cost)
- Link to `RuntimeInstance` via `vpsInstanceId` FK

**Service: `VpsProvisioningService`**
- `provision(workspaceId, config)` — create VPS, install Docker, deploy pro-agent container, register with API
- `decommission(instanceId)` — destroy VPS, mark instance offline
- `getStatus(instanceId)` — poll provider for VPS status
- `scale(workspaceId, action)` — resize VPS (upgrade/downgrade)

**Provider adapters (initially Hetzner only):**
- `HetznerAdapter` — create_server, delete_server, get_server using Hetzner Cloud API
- Interface for future DigitalOcean/AWS adapters

### 2.2 VPS Bootstrap Script
- Cloud-init or SSH-based bootstrap:
  1. Install Docker + Docker Compose
  2. Pull pro-agent image
  3. Generate Ed25519 keypair
  4. Start pro-agent container with env vars pointing to Nexoria API
  5. Pro-agent self-registers via `POST /runner/runtime/instances`

### 2.3 Lifecycle Management
- Auto-shutdown idle VPS instances (no jobs for N hours) to save cost
- Auto-start on new job if workspace has `auto_scale: true`
- Health monitoring: mark instance `error` if heartbeat missed for 2 minutes
- Cost tracking per workspace (VPS hours * rate)

## Known Issues / Technical Debt

1. **`ProAgentRunnerController` has no auth guard** — `ProAgentHttpGuard` exists but is not wired to the controller. The registration and heartbeat endpoints are wide open.
2. **`streamChatEvents()` SSE endpoint** returns empty Observable but is still exposed. Should be removed or deprecated.
3. **`appendWorkspaceActionCards`** in `chat.store.ts` still uses HTTP polling (3s intervals). Should be replaced with `chat.action_card` WS event.
4. **`chat.send` uses `workspaceId` as `sessionId`** — the frontend sends `sessionId: workspaceId` instead of the actual chat session ID. This means all messages go to a session keyed by workspace, not by the actual session.
5. **JWT token missing `workspaceId`** — `authenticateFrontend` reads `decoded.workspaceId` from the JWT, but the auth service may not include it in the token payload. Need to verify.
6. **Pro Agent tools are all stubs** — terminal, fs, execute_code all return "Not yet implemented".
7. **Pro Agent memory is no-op** — `CompositeMemoryManager` in `loop.ts` uses stub providers.
8. **No sandboxing for Pro Agent tools** — when tools are implemented, they need Docker/nsjail sandboxing.

## Key Architecture Decisions

1. **One Pro Agent per workspace** (not per user) — simpler, matches current `findReadyInstance` logic
2. **WebSocket is primary, HTTP is fallback** — REST for CRUD, WS for real-time
3. **Nexoria-managed VPS only in v1** — self-hosted comes later
4. **Default models in v1** — model selection + BYOA is a future phase
5. **`@nexoria/agent-core` is the shared brain** — both lite and pro agents use it; pro extends with more tools
6. **Pro Agent runs on Nexoria-managed VPS** — not user-managed; Nexoria has full lifecycle control
7. **Ed25519 auth for Pro Agent** — already implemented, keep it
8. **No OpenClaw dependency** — the `openclaw-runner` is gone; all agents are native Nexoria

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| VPS provisioning costs spiral | Auto-shutdown idle instances, cost caps per workspace |
| Pro Agent security (shell access) | Sandbox via Docker/nsjail, risk assessment, approval gates |
| WebSocket reliability | DB persistence as fallback, reconnection logic, missed message recovery |
| Agent-core stability | Comprehensive unit tests, gradual rollout (lite first, pro later) |
| Multi-provider VPS complexity | Start with Hetzner only, abstract interface for future providers |
