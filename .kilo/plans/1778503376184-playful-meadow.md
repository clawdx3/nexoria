# Plan: Nexoria Two-Tier Agent Platform

## Vision

Nexoria is a platform for non-technical users to run AI agents. Two tiers:

| Tier | Runtime | Location | Tools | Models (v1) |
|------|---------|----------|-------|-------------|
| **Lite** | `native_saas` | In-process (API container) | Safe tools only (riskLevel <= 2): tasks, memory, search, integrations | Default (gpt-4o-mini or similar) |
| **Pro** | `native_pro` | Nexoria-managed VPS | Full tools: shell, fs, code execution, browser | Default (gpt-4o or similar) |

Future: model selection per agent, BYOA (bring your own API key).

## Known Issues / Technical Debt

1. **`ProAgentRunnerController` has no auth guard** — `ProAgentHttpGuard` exists but is not wired to the controller. The registration and heartbeat endpoints are wide open.
2. **`streamChatEvents()` SSE endpoint** returns empty Observable but is still exposed. Should be removed or deprecated.
3. **`appendWorkspaceActionCards`** in `chat.store.ts` still uses HTTP polling (3s intervals). Should be replaced with `chat.action_card` WS event.
4. **`chat.send` uses `workspaceId` as `sessionId`** — the frontend sends `sessionId: workspaceId` instead of the actual chat session ID. This means all messages go to a session keyed by workspace, not by the actual session.
5. **JWT token missing `workspaceId`** — `authenticateFrontend` reads `decoded.workspaceId` from the JWT, but the auth service may not include it in the token payload. Need to verify.
6. **Pro Agent tools are all stubs** — terminal, fs, execute_code all return "Not yet implemented".
7. **Pro Agent memory is no-op** — `CompositeMemoryManager` in `loop.ts` uses stub providers.
8. **No sandboxing for Pro Agent tools** — when tools are implemented, they need Docker/nsjail sandboxing.

## Key Architecture Decisions

1. **One Pro Agent per workspace** (not per user) — simpler, matches current `findReadyInstance` logic
2. **WebSocket is primary, HTTP is fallback** — REST for CRUD, WS for real-time
3. **Nexoria-managed VPS only in v1** — self-hosted comes later
4. **Default models in v1** — model selection + BYOA is a future phase
5. **`@nexoria/agent-core` is the shared brain** — both lite and pro agents use it; pro extends with more tools
6. **Pro Agent runs on Nexoria-managed VPS** — not user-managed; Nexoria has full lifecycle control
7. **Ed25519 auth for Pro Agent** — already implemented, keep it
8. **No OpenClaw dependency** — the `openclaw-runner` is gone; all agents are native Nexoria

## Phase 6: Self-Learning & Curator (Inspired by Hermes Agent)

### Gap Analysis: Nexoria vs Hermes

| Feature | Hermes Agent | Nexoria Current | Gap |
|---------|-------------|-----------------|-----|
| **Skill lifecycle** | active → stale → archived, usage tracking, pinning | No skills system | Missing entirely |
| **Curator** | Background agent that consolidates/skills weekly, writes reports | No curator | Missing entirely |
| **Memory conflict resolution** | Dedup, contradiction detection, merge | Raw extraction, no dedup | Missing |
| **Task-outcome feedback** | Confidence adjusted by task success/failure | `positiveUses`/`negativeUses` only via manual review | Missing auto-feedback |
| **Cross-session recall** | FTS5 search + LLM summarization | pgvector semantic search | Partial (no FTS, no summarization) |
| **Session compression** | Trajectory compressor for training data | Basic `compactMessages` in loop | Minimal |
| **User modeling** | Honcho dialectic user modeling | `profile` tier memories | Basic |
| **Cron scheduling** | Built-in natural language scheduler | None | Missing |
| **Multi-platform gateway** | Telegram, Discord, Slack, WhatsApp, Signal | Web only | Missing |
| **Proactive memory nudge** | Agent nudges itself to persist knowledge | Passive extraction only | Missing |
| **Skill auto-creation** | Creates skills from complex task solutions | No skills system | Missing |

### 6.1 Memory Curator Service

Create `apps/api/src/modules/memory/memory-curator.service.ts`:

**Purpose**: Second-pass quality evaluation after memory extraction. Prevents duplicate, contradictory, or low-quality memories from accumulating.

**Architecture**:
- Runs as a background task (not cron — triggered when idle, like Hermes)
- `maybe_run_curator(workspaceId)` — checks if last run was > 7 days ago AND no active chat sessions
- Fetches existing memories (top 50 by confidence) + candidate memories from last extraction
- Single LLM call compares candidates against existing:
  - `CREATE` — genuinely new information
  - `UPDATE` — supersedes existing memory (sets `supersededBy`)
  - `MERGE` — combines with existing memory
  - `SUPPRESS` — duplicate or lower-quality version
- Writes structured report to `memory_curator_runs` table

**DB changes**:
- Add `memory_entries.supersededBy` (UUID, nullable) — FK to memory that replaces this
- Add `memory_entries.qualityScore` (float, default 1.0) — separate from confidence
- Add `memory_curator_runs` table: id, workspaceId, startedAt, completedAt, candidatesCount, actions (JSONB), summary

**Integration**:
- Called from `ReflectionDebouncerService` after `extractFromTranscript()` returns candidates
- Or runs independently on a schedule (daily cron, after lifecycle maintenance)

### 6.2 Task-Outcome Feedback Loop

**Purpose**: Automatically adjust memory confidence based on whether recalled memories contributed to successful task outcomes.

**Architecture**:
- `MemoryOutcomeTrackerService` in `apps/api/src/modules/memory/`
- After each agent run completes (`AgentExecutorService.run()` returns):
  1. Get the list of memory IDs that were recalled (`MemoryContextBuilder` already tracks this via `touchValidatedAt`)
  2. If `result.success === true`: increment `positiveUses` on recalled memories
  3. If `result.success === false`: increment `negativeUses` on recalled memories
- This replaces the manual `/memory/:id/review` endpoint for automatic cases
- Manual review still available for explicit user feedback

**Integration point**: `AgentExecutorService.run()` — after `reflection.reflect()` call, also call `memoryOutcomeTracker.recordOutcome(ctx, result)`.

### 6.3 Memory Conflict Resolution

**Purpose**: Detect and resolve contradictory memories (e.g., "User prefers formal tone" vs "User prefers casual tone").

**Architecture**:
- Part of the Curator service (6.1)
- When the curator detects two memories with conflicting content:
  - Keep the newer one (higher `createdAt`)
  - Set `supersededBy` on the older one
  - Log the conflict in `memory_curator_runs.actions`
- Also detect near-duplicate memories (similar content, different wording):
  - Merge into the higher-confidence entry
  - Set `supersededBy` on the duplicate

### 6.4 Proactive Memory Nudge

**Purpose**: Instead of only extracting memories passively, the agent should occasionally nudge itself to persist important knowledge.

**Architecture**:
- Add a `nudge_memory` tool (riskLevel 1, exclusive false)
- The orchestrator's system prompt includes: "After completing a significant task or learning something important about the user, use `nudge_memory` to ensure it's persisted."
- `nudge_memory` calls `ReflectionService.extractFromTranscript()` immediately (bypassing debounce) for the current session
- Or writes directly to memory with a higher confidence (0.95) since it's agent-intentional

**Integration**: Register in `ToolRegistryService.registerBuiltIns()`, add to orchestrator's `enabledTools`.

### 6.5 Context Engine Abstraction (Inspired by Hermes)

Hermes has a pluggable `ContextEngine` ABC that controls how conversation context is managed when approaching token limits. Nexoria's current `compactMessages` is a basic heuristic. Adopt the pattern:

**Create `packages/agent-core/src/context-engine.ts`**:
- `ContextEngine` interface: `shouldCompact(messages)`, `compact(messages, focusTopic?)`, `updateFromResponse(usage)`, `onSessionStart()`, `onSessionEnd()`
- `DefaultCompactionEngine` — current logic (protect system + last 4 turns, replace older tool results)
- `SummarizationEngine` — uses a cheap LLM to summarize older turns (like Hermes' IterativeSummarizer but as a first-class engine)

**Wire in `AgentConfig`**:
- Add `contextEngine?: ContextEngine` field
- If provided, use it instead of the built-in `compactMessages`
- Default to `DefaultCompactionEngine` when `enableCompaction: true`

This enables future context engines (DAG-based, LCM, etc.) without changing the loop.

### 6.6 Skills System (Future — Not in v1)

Hermes has a full skills system with:
- `SKILL.md` files with template variables, inline shell preprocessing
- Skill lifecycle: active → stale → archived
- Usage tracking, pinning, consolidation by curator
- Skills Hub for sharing (agentskills.io)

For Nexoria v1, the "skills" concept maps to:
- **Agent profiles** with different `systemPrompt` + `enabledTools`
- **Subagent spawner** (already implemented) acts as skill dispatch

A full skills system can be added later as:
- `skills` table: name, content (markdown), workspaceId, lifecycle state, usage count
- Skills loaded into agent context like memory (injected into system prompt)
- Curator manages skill lifecycle (consolidate, archive, reactivate)

### 6.6 Cron Scheduling (Future — Not in v1)

Hermes has a built-in cron scheduler for recurring tasks. For Nexoria:
- Add `scheduled_tasks` table: workspaceId, cron expression, agentProfileId, prompt, deliveryTarget
- A cron worker (BullMQ or @nestjs/schedule) fires jobs at the scheduled time
- Results delivered via WebSocket or stored as tasks

### Key Takeaways from Hermes

1. **Curator runs on idle, not cron** — waits for `min_idle_hours` (2h) + `interval_hours` (7 days). This prevents the curator from competing with active agent work.

2. **Skills have states** — active → stale (30 days no use) → archived (90 days). Pinned skills bypass transitions. This prevents skill library bloat.

3. **Memory has lifecycle hooks** — `on_turn_start`, `on_session_end`, `on_delegation`, `on_pre_compress`, `on_memory_write`. This lets providers react to agent events, not just passive reads.

4. **Context engines are pluggable** — the `ContextEngine` ABC lets you swap compaction strategies without changing the agent loop.

5. **Streaming scrubber** — strips memory-context fences from streamed output so internal memory doesn't leak to users. Nexoria already has `StreamingScrubber` in `packages/agent-core/src/memory/provider.ts`.

6. **Trajectory compression** — for RL training data. Not directly applicable to Nexoria's SaaS use case, but useful if we ever want to fine-tune models on agent interactions.

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| VPS provisioning costs spiral | Auto-shutdown idle instances, cost caps per workspace |
| Pro Agent security (shell access) | Sandbox via Docker/nsjail, risk assessment, approval gates |
| WebSocket reliability | DB persistence as fallback, reconnection logic, missed message recovery |
| Agent-core stability | Comprehensive unit tests, gradual rollout (lite first, pro later) |
| Multi-provider VPS complexity | Start with Hetzner only, abstract interface for future providers |
